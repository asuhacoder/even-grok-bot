# Even Hubへのデプロイ

Webサーバーの更新だけで完了とはせず、Even Hubへのアップロードと指定された配信状態の確認まで行う。

このプロジェクトはEven HubでPublic公開しない。利用者がそれぞれ自分でG2アプリをビルドし、自分のEven Hub開発者アカウントのプロジェクトへBeta（非公開テスト）ビルドとして入れ、自分の中継へ向ける。到達点はPrivateまたはBetaだけである。

## 基本方針

- 個人情報を調査しない。メール、履歴、他のプロジェクト、保存済みパスワードなどを探索しない。
- アカウント名、絶対パス、端末名、IP、ホスト名、プロセスID、ウィンドウIDは利用者ごとに異なる。過去の環境の値を流用しない。
- 対象リポジトリの設定・手順を優先し、利用者の未コミット作業を上書きしない。
- ブラウザ操作には利用可能な承認済みツールを使い、その手順・権限に従う。権限拒否を別経路で回避しない。
- ログインが必要なら利用者に依頼するか、承認済みの認証手段を使う。秘密値をログやスキルに保存しない。
- 使うのは利用者自身のEven Hubアカウントとプロジェクトだけ。他人のアカウント、共有のプロジェクト、共有の中継を前提にしない。
- アップロード、Private、Betaを別の段階として扱い、配信対象を勝手に広げない。Public公開・審査提出は行わない。

## 1. 対象とゴールを確認する

1. 作業ディレクトリ、Gitの状態、README、パッケージ設定、アプリのマニフェストを確認する。
2. 対象アプリ、package ID、今回のバージョン、ビルド方法を特定する。アプリのバージョンはマニフェストを基準とし、開発用パッケージのバージョンと混同しない。
3. アプリパッケージのほかに、中継や配信用Webサーバーの更新が必要かを確認する。
4. 配信のゴールを確認する。既存Betaの更新を依頼されているならBetaまで、アップロードのみならPrivateまでとする。曖昧なら変更前に質問する。Public公開や審査提出を頼まれたら、このプロジェクトでは行わないと伝えて止める。Betaの配信対象の追加は明示的な指示なしに行わない。
5. 同じバージョンが登録済みなら状態を確認し、重複アップロードやバージョンの無断変更を避ける。

## 2. 検証・ビルド・パッケージ作成

1. リポジトリ所定のテスト、型検査、本番ビルドを実行する。失敗したら原因を確認してから次へ進む。
2. 既存のパッケージ作成スクリプトを実行する。なければ、インストールされているEven Hub CLIのヘルプで構文を確認してから使う。
3. pnpmでは `pnpm pack` がパッケージマネージャー自身のコマンドになることに注意する。`pack` という名前のスクリプトは `pnpm run pack` で明示的に実行する。
4. `.ehpk` が新たに生成されたこと、対象バージョン、SDK・最低アプリバージョン等のCLI結果を確認する。古いパッケージを使わない。
5. `.ehpk` の内部形式を決めつけない。内容の検証には対応した手段を使い、ZIPとして読めるとは仮定しない。
6. 中継やWeb配信も更新する構成なら、既存の運用手順で反映し、必要なヘルスチェック・接続確認を行う。これはEven Hubへのアップロードとは別工程である。

## 3. 利用者自身のブラウザからアップロードする

1. 使用するブラウザと対象ウィンドウを特定し、最新の画面を確認する。古い要素番号や座標を使い回さない。
2. [Even Hub](https://hub.evenrealities.com/) のConsoleを開く。ログイン済みなら既存セッションを使い、必要な範囲だけを閲覧する。
3. My projectsで対象の既存プロジェクトを開く。既存アプリの更新では、新規プロジェクト作成用の「Upload package」ではなく、対象プロジェクトの「Upload a build」を使う。表示文言は変わることがあるため、実画面で意味を確認する。
4. ファイル選択から、今回生成した `.ehpk` を指定する。
5. ファイルダイアログが閉じただけでは成功としない。Web画面上に正しいバージョン、パッケージ名、サイズ等が表示されたことを確認する。
6. 「Add build」等の最終確定操作を行う。
7. ビルド一覧に対象バージョンが「Uploaded」「Private」等として追加されたことを確認する。

### ファイル選択で止まった場合

- 最新の画面と選択状態を確認する。操作の成功応答だけを根拠に同じクリックを繰り返さない。
- ページのファイル入力に対応した許可済みツールがあれば、正確な入力要素にローカルファイルを設定する。
- ネイティブダイアログはブラウザとは別のOSプロセスで管理される場合がある。使用ツールの正式な対応方法で所有者と対象を特定し直す。
- 意図したファイルの選択と「開く」が有効なことを確認する。キャンセル・タイムアウト後は現在の状態を確認してから再開する。
- 既存プロジェクトの更新フローか、新規作成フローかを再確認する。
- 権限やツールの制約が原因なら必要な最小限の操作を利用者に依頼する。権限境界を迂回しない。

## 4. 指定された配信先へ反映する

### Privateまでの場合

対象ビルドがPrivate一覧に登録されたことを確認して終了する。BetaやPublicに配信されたとは報告しない。

### Beta更新の場合

1. アップロードした対象バージョンのBuild detailsを開く。
2. 配信状態のコントロールからBetaへの昇格を選ぶ。
3. 確認画面で対象バージョンと既存Betaグループを確認する。メンバーの追加・変更は行わない。
4. 「Promote to Beta」等で確定する。
5. プロジェクト画面で「Beta build」が新バージョンになり、「Published」「Beta」等の配信済み状態であることを確認する。可能なら再読み込み後も同じ状態であることを確認する。

Public配信・審査提出はこのプロジェクトでは行わない（AGENTS.md参照）。

## 5. 完了条件と報告

次を区別し、確認できた事実だけを簡潔に報告する。

- ローカル検証・ビルドの結果。
- Even Hubに登録されたバージョン。
- 配信状態：Private、Beta等。
- 中継・Web配信を更新した場合は、その稼働確認結果。
- 利用者側で必要な更新・再起動等。端末上のインストール・動作を未確認なら明記する。

成功例：

> vX.Y.ZをEven Hubへアップロードし、Betaへの反映を確認しました。ポータルのBeta buildはvX.Y.Z／Publishedです。端末側の更新・動作確認は未実施です。

未完了なら「パッケージ作成済み」「Private登録済み」など到達点と残作業を示す。Webサーバー更新やアップロードボタンのクリックだけで「デプロイ完了」と言わない。
